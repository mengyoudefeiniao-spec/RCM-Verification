# 离线人脸核验 App（技术验证版 v2.3）

> 1:1 人脸比对 + 活体检测，**全程不联网**。MediaPipe Face Mesh 做活体挑战，ArcFace(AAM-Softmax) 做特征比对。
>
> **v2.0 新增「证件核验」**：卡背 OCR 识别家庭编号与 MRZ（PP-OCRv4）+ 手机 NFC 读取 ICAO 9303 芯片
> 的 DG1/DG2/DG11 并做被动认证（PACE-ECDH-GM / BAC）。见下面「证件核验」一节。
>
> **真机验收（v1.7 人脸部分）**：安装正常 · 建模成功 · 活体三个动作全部通过 · 同人相似度 0.50–0.70（>阈值 0.45）。
> 证件核验部分**尚未上真机/真卡**（原因与替代验证见「证件核验」与 VERIFICATION.md 第 15 节）。

## 交付物：两个版本，按体积/精度二选一

| 文件 | 体积 | 识别模型 | 默认阈值 | 包名 / 桌面名称 | 适用 |
|---|---|---|---|---|---|
| `out/FaceVerify-lite.apk` | **72 MB** | ArcFace MobileFaceNet（13 MB） | **0.58** | `iq.digitalration.faceverify.lite` / 离线人脸核验 Lite | 体积/低端机优先 |
| `out/FaceVerify-offline.apk` | 225 MB | ArcFace R50 @Glint360K（166 MB） | **0.45** | `iq.digitalration.faceverify` / 离线人脸核验 R50 | 精度优先 |

v2.0 起两个包都包含**证件核验**（卡背 OCR + NFC 芯片），比 v1.7 各多 **21.4 MB**（检测 4.5 MB + 英文/数字识别 7.5 MB + 阿拉伯文识别 8.6 MB + 字典）。
v2.1（versionCode 11）：拍卡改用后置摄像头、NFC 改为贴卡自动感应。
v2.2（versionCode 12）：OCR 换成"英文/数字 + 阿拉伯文"双模型、白名单解码、二值化重试、认标签定位户号、MRZ 校验位反解、连拍两帧投票。
v2.3（versionCode 13）：户号结构改为"4 数字 + 1 字母 + 13 字母数字"（真卡尾部会带字母）、多尺度集成识别、歧义位给候选值、可手工改正；读芯片后用 DG11 反校 OCR。

两个包是**两个不同的应用**（包名不同、桌面名称不同）：**可以同时装在一台手机上，后装的不再覆盖先装的**。
数据目录按包名隔离，所以各自的参照照片、阈值、调试图互不干扰——正好可以拿同一批照片在两个版本上各跑一遍做对比。
同一版本内的重复安装是原地升级（包名不变，桌面上的图标不会被复制成两个）。

顺带修掉一个旧隐患：以前两个包共用一份数据，从标准版换成精简版时 `SharedPreferences` 里的 `thr` 还在，`App.readModelConf()` 只在「没有 thr」时才写入默认值，于是精简版会沿用 0.45 而用不到它标定好的 0.58。包名分开后各存各的，阈值、参照特征、调试图都跟着版本走。

体积构成（标准版）：模型 166 MB + 原生库 30 MB（仅 arm64）+ MediaPipe 模型 3.6 MB + 代码 4.7 MB。
早先 225 MB 是因为同时打了 armv7 的库（+20 MB）；32 位机型已不再支持。

**精度差异（FairFace MiddleEastern 350 张，异人对）**：

| 模型 | 异人相似度均值 | 最大 | >0.45 占比 | FAR=1e-3 所需阈值 |
|---|---|---|---|---|
| R50 | 0.063 | 0.208 | 0.07% | ≈0.43 |
| MobileFaceNet | 0.216 | 0.390 | 3.24% | ≈0.58 |

小模型的嵌入空间更"挤"（异人均值高 3.4 倍），**所以不能沿用 0.45**——精简版默认 0.58 就是按 FAR≈1e-3 标定的。
另外注意：这是异人单侧分布，同人侧（FRR）需要真实人像对才能测，目前没有。

## 安装与测试

1. 把 `out/FaceVerify-offline.apk` 传到手机（微信/QQ 传文件、数据线、网盘都行），点击安装。
   - 需要允许「安装未知来源应用」。
   - 手机剩余空间要 ≥ 500 MB：APK 本身 224 MB + 首次启动会把 166 MB 模型复制到应用私有目录。
2. 首次启动会显示「复制模型…」，**约 5–20 秒**（视手机闪存速度），之后秒开。
3. **先点「自检」**（不需要相机/相册）：它会跑一遍检测→对齐→特征，显示每个环节的毫秒数与两个一致性数值，并把手里的 112×112 对齐结果画出来。这一步能直接确认模型在你机器上是否正常、跑得多快。把截图发我。
4. 点「① 从相册选择一张人像」→ 选一张你自己的清晰正脸照 → 等 1～3 秒，出现特征维度和建模耗时即成功。
5. 点「② 开始核验」→ 屏幕会显示相机画面（**所见即算法所见**）→ 按提示完成 3 个随机动作（眨眼／转头／张嘴／微笑中随机 3 个）。
6. 活体通过后自动采集 6 帧并比对，弹出结果：相似度、阈值、活体证据、耗时、调试图路径。
   采集时会做**几何门控**：5 点不合理（歪头/遮挡/误检）的帧不参与比对，并提示具体原因。
7. 可选「③ 评测模式」：多选一批人像 → 本地算出 FAR/FRR/EER 并给出建议阈值，一键应用到核验。
8. 可选「**双图比对**」：再选一张照片，与参照照片做 1:1 比对——**不需要相机**，用来单独验证核心算法。
   会输出相似度、阈值判定、各阶段耗时、检测点数、人脸占比、清晰度，以及两张对齐图并排。
9. 可选「**证件核验**」：卡背光学识别（家庭编号 + MRZ）+ NFC 读芯片。步骤见下面「证件核验」一节。
   只想验证芯片时，可以先在界面里手输 MRZ 三项（证件号/出生/有效期），不用相机。

**验证"不联网"**：开飞行模式，整个流程照样跑通（模型、推理、比对全在手机本地）。

### 出问题时怎么反馈

- 主界面底部会自动显示上一次崩溃的堆栈（`last_crash.txt`），截图发我就行。
- 每次核验完会存一张**调试图**（参照照片 + 本次各帧的 112×112 对齐结果并排），路径写在结果页里：
  `Android/data/<包名>/files/debug/verify_*.png`（标准版 `<包名>` = `iq.digitalration.faceverify`，精简版 = `iq.digitalration.faceverify.lite`）。这张图能直接看出对齐有没有歪。
- 核验页左下角有实时状态行：`人脸 N 个 · yaw 0.12 · 脸宽 168px · 帧 480x640`。如果画面是横的/倒的，说明旋转判断错了 → 回主界面「调试 → 分析帧旋转」手动选 90 或 270。

## 证件核验（卡背 OCR + NFC 芯片）

主界面「证件核验（卡背 OCR 家庭编号 + NFC 芯片）」进入，一个界面做两件事，对应两张参考截图。

### ① 卡背光学识别（v2.3，后置摄像头，离线不联网）

**要认的第一个东西是「家庭编号」**，也就是卡背 `الرقم العائلي :` / `ژمارەی خێزانی :` 后面那个
18 位编号。两位真实样例说明它**不是纯数字**：

```
1002 E 6996574360150     4 位数字 + 1 位字母 + 13 位数字
1002 L 00M9770006805     4 位数字 + 1 位字母 + 13 位"字母数字"（尾部还可以带字母）
```

所以规则是：**前 4 位必须是数字，第 5 位必须是字母，后 13 位是字母数字**（数字 ≥13、字母 ≤4）。
尾部字母只有在"不像数字"时才保留（M/C/F/H/K/N/R/U/V/W/X/Y），像数字的字母（O/I/S/B/Z/G/D/Q/T/A/E/P）
才按置信度决定是否改成数字。

v2.2 相比 v2.0/v2.1 的改动（v2.0 用中文 PP-OCRv4 模型，对卡面数字和阿拉伯文都不太行）：

| 改动 | 为什么 |
|---|---|
| 识别模型换成 **en_PP-OCRv3_rec**（436 类 ASCII）+ **arabic rec**（161 类阿拉伯字母）双模型 | 中文模型的 6625 类里全是汉字，18 位数字长串会被汉字类抢票；英文模型字符集只有 ASCII，数字行一次过的比例高得多。阿拉伯文模型专门读标签 |
| CTC 解码加**白名单**（只用 0-9 A-Z `<`） | 去掉小写字母、标点、汉字的干扰，`l` 不再抢 `I` 的位置 |
| 低置信度行自动**二值化重试**（Otsu） | 卡面底纹/水印/反光把笔画和背景拉近时，二值化后识别率明显上升 |
| 缩放换成**面积平均 + 双线性**（原来是最近邻） | 最近邻会让小字号出现马赛克、大字号出现摩尔纹，两个都伤识别 |
| **认标签再认值** | 只在「الرقم العائلي / ژمارەی خێزانی」那一行（或紧邻的左/下一行）里找编号，避免把卡上别的长数字当成户号。标签归一化后模糊匹配（`ژ→ز`、`ێ→ي`、`ە→ه`，编辑距离 ≤2） |
| 家庭编号**位置感知纠错 + 代价** | 前 4 位按数字修、第 5 位按字母修，改动 ≤3 处才接受；依旧不靠"猜" |
| MRZ 用**校验位反解** | 在 `0↔O、1↔I、5↔S、8↔B、2↔Z、6↔G、4↔A、7↔T、3↔E、9↔P` 里枚举 ≤2 处替换，找到让 ICAO 7-3-1 校验位成立的组合——一个字符读错不再毁掉整张卡的 BAC 密码 |
| 连拍 **2 帧投票** | 点一次「拍摄识别」取最近 2 帧；第一帧就"户号 + MRZ 齐全"时不再跑第二帧。同一位错成同一个字符的概率低，逐位取多数能修掉单帧错误 |
| **多尺度集成**（v2.3） | 长 alnum 行（户号/MRZ/日期）在 1.0×、1.35× 宽度和原图/二值化上各识别一次，逐位按该位的模型概率加权投票。`M→4` 这类错误在不同尺度上不会同时发生，集成后多数能被纠正 |
| **歧义位给候选 + 手工改正**（v2.3） | 逐位记录次优字符，把"4 也可能是 M"这类位置列成候选值显示在界面上；另加「改正家庭编号」输入框，人工一眼能改对。读芯片后若 DG11 与光学值只差 1~3 位，直接判为 OCR 认错、以芯片为准并说明差异位置 |

其它行为不变：

- 拍照用**后置摄像头**；界面是"当前帧定格预览"，卡对好框后**稳 0.3 秒再按**。没有后置自动退回前置并提示。
- 照片**横着拍/倒着拍都能认**：先用 480px 小图在 0/90/180/270 比较"文字概率面积"选方向，
  单行再用二阶矩定轴 + 逐行 0°/180° 试别（阿拉伯文行会标记 `rtl`，输出前整体反转成正常阅读顺序）。
- 认不出 MRZ 时「手输 MRZ」兜底（证件号 / 出生 YYMMDD / 有效期 YYMMDD），读芯片不依赖相机。

| 环节 | 选型 | 体积 |
|---|---|---|
| 文字检测 | PP-OCRv4 det（DBNet，ONNX，1280 最长边） | 4.5 MB |
| 编号/MRZ 识别 | en_PP-OCRv3_rec（CTC，436 类 ASCII，行高 48） | 7.5 MB |
| 阿拉伯文标签识别 | arabic rec（CTC，161 类） | 8.6 MB |
| 字典 | `ppocr_keys_en.txt` / `ppocr_keys_ar.txt` | 2 KB |

模型来自 HuggingFace `monkt/paddleocr-onnx`（PaddleOCR 官方模型的 ONNX 导出版；检测模型沿用
`SWHL/RapidOCR` 的 PP-OCRv4 det）。全部塞在 `assets/`，运行时零网络、零 GMS——**飞行模式下可用**。
推理走 App 已有的 ONNX Runtime（与 ArcFace 同一个 native 库），没有引入新的原生依赖。

### ② NFC 读 ICAO 9303 芯片（靠近自动读）

**是"贴上去自动读"，不用反复点按钮**：MRZ 一就绪（OCR 成功或手输完成），App 会自动打开 NFC 感应
（`NfcAdapter.enableReaderMode`），此后把卡贴到手机 NFC 区域就自动开始读；读成功后自动关闭感应
（避免重复触发），失败则保持感应，重新贴一次即可重试。切到后台或退出页面会关闭感应，回来时自动恢复。

- 贴卡位置：多数机型在**背面上半部、摄像头附近**；不确定就左右上下慢慢挪，感应到会有系统提示音。
- 必须保持贴合：读 DG2 人像要发上百条 APDU，**5~15 秒**，中途拿走会中断（提示"读卡中断，可重贴重试"）。
- NFC 没开时界面会直接告诉你去系统设置打开，回来后自动恢复感应。
- 感应到的是普通 NDEF 标签（不是证件芯片）时会明确提示"不是 ISO-DEP 芯片"，不会误报成功。

芯片读出的内容：

- **DG1**：机读区（证件号、签发国、国籍、出生、性别、有效期、姓名 + 各校验位）
- **DG2**：芯片内人像（JPEG 可直接显示；JPEG2000 在 Android 上无系统解码器，只显示字节数并说明原因）
- **DG11**：附加信息（全名、个人编号/家庭编号——**和光学识别的家庭编号做一致性比对**、完整出生日期、出生地、地址等）
- **EF.SOD**：CMS 签名 + 各数据组哈希，给出四项判定（对应参考截图里的"芯片状态"）：

| 判定项 | 本 App 的做法 | 含义 |
|---|---|---|
| SOD 完整性认证 | 用 SOD 内自带的证件签名证书验 CMS 签名（含 signedAttrs 的 messageDigest） | SOD 未被篡改 |
| 数据组哈希（芯片认证） | 对读到的 DG1/DG2/DG11 重算哈希，与 SOD 声明值逐个比对 | 芯片数据未被改写 |
| 证书链自洽 | DS 证书的签发者能在 SOD 内找到且签名可验证 | 链自洽，**但未锚定 CSCA** |
| 签名证书有效性 | `X509Certificate.checkValidity()` | 当前时间在证书有效期内 |

> 「这张证件由伊拉克签发」必须导入伊拉克的 CSCA 主列表才能判定，本版**没有**主列表，
> 所以只报"自洽/未锚定"，不会把"签名有效"说成"证件真实"。

访问控制按芯片能力自动选择：

- **PACE-ECDH-GM**（AES-128/192/256、3DES）：先从 EF.CardAccess 读芯片声明的参数，
  支持 NIST P-192~P-521 与 brainpool P192r1~P512r1（曲线参数内置，**不依赖 JCE 的 brainpool 支持**，
  Android/Conscrypt 与 JDK/SunEC 对 brainpool 的支持并不一致）。
- 失败或芯片不支持时回退 **BAC**（3DES 安全报文）。
- 未实现：PACE-DH-GM、PACE 的 Integrated/Chip Authentication Mapping。遇到只支持这些的芯片，
  界面会明确报"PACE 失败，回退 BAC"，不会静默失败。

  样本在 `tools/fixtures/nfc-sample/`，由 `tools/nfc-proto/gen_nfc_sample.py` 生成（含自签 DS/CSCA）。

### 这一块没验证的地方（重要）

1. **没有真机 NFC**。APDU 层只在"假芯片"上跑通；真实卡的时序、`6Cxx`/`61xx` 兼容性、
   读 30KB 人像要多久（约 150 条 APDU）都只能在手机上确认。
2. **没有真实卡背照片**。OCR 只在合成图上验证（Arial 近似的印刷体），真实卡面的底纹、阿拉伯文、
   反光、竖排字号都可能让检测框变差；家庭编号的格式也只有截图这一种样例。
3. **JPEG2000 人像解不出来**。Android 的 BitmapFactory 不支持 JP2，如果芯片用 JP2，只能看到字节数。
4. **CSCA 主列表没做**。所以"被动认证"目前只能证明"数据与 SOD 一致、SOD 签名自洽"，
   不能证明证件由某国签发。

## 技术方案

| 环节 | 选型 | 为什么 |
|---|---|---|
| 人脸检测 + 网格 | **MediaPipe Face Landmarker**（`face_landmarker.task`, float16, 3.5 MB）478 点 + 52 blendshape | Face Mesh 本身只给几何，但它的 blendshape 直接输出 `eyeBlinkLeft/Right`、`jawOpen`、`mouthSmile`，比手算 EAR 稳；活体判定就是靠它 |
| 活体 | **挑战-响应**：从 {眨眼, 转头, 张嘴, 微笑} 里随机抽 3 个，顺序随机，每个都有超时重试 | 静态照片无法在时序上完成眨眼/转头；随机顺序防预录视频 |
| 人脸对齐 | 5 点相似变换（Umeyama）→ 112×112，模板与 insightface `norm_crop` 完全一致 | ArcFace 对对齐极敏感，用官方模板才能吃到模型原精度 |
| 特征提取 | **ArcFace R50 @ Glint360K**（`w600k_r50.onnx`, 166 MB, ONNX Runtime 1.20 CPU）512 维 | 比 MobileFaceNet 精度高一大截，且只在前几帧跑一次，延迟可接受（实测见下） |
| 比对 | 余弦相似度，多帧平均 + 水平翻转 TTA | 平均 6 帧降噪，翻转 TTA 消掉对齐镜像误差 |

管线：`相机帧 → MediaPipe(478点+blendshape+yaw) → 5点对齐 112×112 → ArcFace → L2 归一化 → 与参照照片特征算余弦 → 阈值判定`

所有资源都在 APK 里（`assets/`），零网络依赖，零权限除了相机（选图走系统 `ACTION_OPEN_DOCUMENT`，不需要存储权限）。

## 已经验证过的部分（桌面复现，非手机）

因为这台机器没有可用的 adb 设备，**以下都是在 PC 上用 onnxruntime 跑同一个 `.onnx` 得到的**，代码路径与 App 内一致：

- **模型接口**：`w600k_r50.onnx` 输入 `[N,3,112,112]`、输出 `[1,512]`；预处理 RGB + `(x-127.5)/127.5` + NCHW，与 insightface 官方一致。
- **特征判别力**（LFW 8 个不同身份，28 对）：
  - 不同人：均值 **0.063**，最大 0.208
  - 同一张图水平翻转（等同"同一人"）：均值 **0.827**
  - → 0.45 的默认阈值落在这两个分布中间，留有余量。
- **对齐算法**：把图旋转 20° 后用"同样旋转后的 5 点"重新对齐，两张 112×112 裁剪余弦 **0.997** → Umeyama + 双线性 warp 无错。
- **对齐对关键点误差的敏感度**（250px 人脸，单点沿 x/y 各偏 d 后与原裁剪比，n=6）：

  | 偏移 | 3px | 6px | 12px | 20px |
  |---|---|---|---|---|
  | 眼外角 | 0.987 | 0.969 | 0.931 | 0.878 |
  | 鼻尖 | 0.994 | 0.985 | 0.964 | 0.930 |
  | 嘴角 | 0.991 | 0.979 | 0.953 | 0.912 |

  → MediaPipe 的正常定位误差（1~3px）只影响 <1.5%，**关键点索引选偏几个像素不会毁掉精度**；鼻尖最不敏感，眼睛最关键。
- **APK 结构**：`resources.arsc` 未压缩且 4 字节对齐、native 库未压缩、v2+v3 签名校验通过、关键类（MediaPipe/ORT/guava）都在 dex 里。
- **FAR/FRR 统计代码**（`Stats.java` 不依赖 Android，直接 `main()` 自测）：
  - 完全可分数据 → EER **0.00%**，目标 FAR 阈值落在两类之间；
  - 高斯分离（μ=0.62 vs 0.12，σ=0.10）→ EER **0.25%**（与理论 Φ(-2.5)=0.62% 同量级，样本 400 的分辨率就是 0.25%）；
  - 高度重叠（μ=0.40 vs 0.30，σ=0.12）→ EER **34.9%**（理论 ≈34%）→ 公式实现正确。

## 没验证、也别当真的部分（很重要）

1. **没有真机跑过**。相机旋转、帧率、机型差异这些只能上手机才知道。所以我把预览改成"直接显示算法分析帧"，方向错了肉眼立刻能看出来，也能在设置里手动改旋转。
2. **被动反欺诈（打印/屏幕翻拍）没做**。我下载并实测了一个公开的 MiniFASNetV2 ONNX，**在 4 种预处理下输出恒定（0.99 全给同一类），对真脸和屏幕翻拍零区分度**——是个坏模型，所以我把它删了，没有拿假分数糊弄。现在能防的是"静态照片 + 简单视频"，**防不住高质量视频重放**，那必须上经过样本训练的被动模型（见下文）。
3. **伊拉克人群精度没测过**。这版用的是 Glint360K 训练的通用模型，中东人脸在训练集里有覆盖但不是重点；理论性能会略低于官方 LFW 99.8%。**要"保证准确率"必须用真人数据标阈值**，见下节。
4. **证件核验（OCR + NFC）没有真机和真卡验证**。OCR 只在合成卡背图上跑通；NFC 协议栈只在"假芯片"上跑通（详见「证件核验」一节的未验证清单）。

## 怎么把精度"适配伊拉克人"

阈值 0.45 是通用起步值，别直接当 KPI。正确做法（App 已具备条件）：

1. 收集本地数据：**每人 2–3 张**（不同时间/光照/角度）+ 若干"非同人"对照，至少 30–50 人、上千对。
2. 把照片放进手机，文件名按 `人名_序号.jpg` 命名（`iraq001_a.jpg`、`iraq001_b.jpg` 为同一人）。
3. App 里点「③ 评测模式 → 选择照片（可多选）」→ 自动输出同人/异人分布、ROC 表、EER、以及按目标 FAR 的建议阈值 → 点「应用建议阈值」直接生效。
4. 选 FAR 档位：
   - 门禁/核身类（误接受要极低，FAR=1e-3）→ 阈值通常 0.50~0.55
   - 体验优先（FAR=1e-2）→ 0.40~0.45
5. 记录 EER 作为基线。若 EER 明显差于 3%~5%，再考虑换模型（见下）。

下一步可选的模型升级（都需要联网下载，本次未做）：
- `buffalo_l` 的 `w600k_r50`（也就是现在这个）已是最常用的高质量开源档；
- 想再进一步：`glintr100`（R100，248 MB）或 adaface/Arc2Face 系列；
- 想更快：`w600k_mbf`（13 MB，精度降 1~2%），适合低端机。

## 重新构建

```powershell
pwsh -File tools\build.ps1               # 标准版 R50  → out/FaceVerify-offline.apk  包名 iq.digitalration.faceverify
pwsh -File tools\build.ps1 -Model mbf    # 精简版 MBF  → out/FaceVerify-lite.apk     包名 iq.digitalration.faceverify.lite
pwsh -File tools\test.ps1                # JVM 单测（对齐矩阵/活体状态机/FAR 统计）
```

**模型 → 应用标识**的映射写在 `tools/build.ps1` 的「每个模型 = 一个独立应用」段：默认 r50 用原包名（保留升级路径），mbf 加 `.lite` 后缀，桌面名称分别是「离线人脸核验 R50 / Lite」。
包名是通过 `aapt2 link --rename-manifest-package` 在生成 APK 时改的，`app/AndroidManifest.xml` 和 Java 源码都不用动（R 类仍在 `iq.digitalration.faceverify` 下）。
要临时换个标记（比如同时留多个试验包）可加参数：`-PackageSuffix .r50test -AppLabel "核验 R50 试验" -Out FaceVerify-r50test.apk`。
新增模型时：在 `param` 的 `ValidateSet` 里加名字，并在同段给出对应的包名后缀/桌面名/默认阈值。

依赖已经在本机准备好（`sdk/` 里是 JDK17 + build-tools 35 + platform 35，`dl/maven` 里是 MediaPipe/ORT 的 AAR）。注意：`aapt2` 遇到绝对中文路径会报 `Illegal byte sequence`，脚本已全部改用相对路径，别改回去。

构建还需要 `models/` 下的 OCR 资源：`ppocr_det.onnx`、`ppocr_rec.onnx`、`ppocr_keys_v1.txt`（脚本会检查，缺了直接报错）。
`EcCurve.java` 是生成文件：改曲线请改 `tools/gen_curves.py` 后重跑（NIST 参数取自 JDK，brainpool 取自 RFC 5639）。

`tools/build.ps1` 存成 **UTF-8 with BOM**：本机是 PowerShell 5.1，它会把**没有 BOM** 的 `.ps1` 按系统 ANSI 解码，脚本里的中文（默认阈值说明、桌面名称）就会变乱码并写进 APK。用编辑器改完请确认 BOM 还在。

## 后续建议

- 拿到你的真机反馈后，优先修：相机旋转、帧率、首启复制耗时。
- 要做"能防翻拍"的版本，需要一批真实的攻击样本（打印照片、手机屏幕、iPad 回放），再训练/微调一个被动模型——这是目前最大的缺口。
- 想上线级应用，还要补：活体动作的防注入（摄像头帧签名）、特征加密存储、活体与比对的时序绑定。
