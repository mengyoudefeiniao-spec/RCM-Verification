# 离线人脸核验 App（技术验证版 v2.3）

> 1:1 人脸比对 + 活体检测，**全程不联网**。MediaPipe Face Mesh 做活体挑战，ArcFace(AAM-Softmax) 做特征比对。
>
> **v2.0 新增「证件核验」**：卡背 OCR 识别家庭编号与 MRZ（PP-OCRv4）+ 手机 NFC 读取 ICAO 9303 芯片
> 的 DG1/DG2/DG11 并做被动认证（PACE-ECDH-GM / BAC）。见下面「证件核验」一节。
>
> **真机验收（v1.7 人脸部分）**：安装正常 · 建模成功 · 活体三个动作全部通过 · 同人相似度 0.50–0.70（>阈值 0.45）。
> 证件核验部分**尚未上真机/真卡**（原因与替代验证见「证件核验」与 VERIFICATION.md 第 15 节）。

真机上点下去仍然让按指纹，前置摄像头根本没启动（报告里 `authType=2`、`weakAuth` 就是那次按手指）。
现在新增 `FaceLoginActivity`：前置相机 + MediaPipe 活体挑战（随机 3 个动作）+ 采集 6 帧对齐后

证据强度照实标注：`cryptoBound=false`（2D 人脸解锁不了 Keystore 生物密钥）、
`identityBound=true/false`（没登记参照时只证明"镜头前是真人"，不证明是谁）；
结果写进 `lab.json` 的 `results.bio.faceAuth`，报告 TV-05 一行会带上「前置人脸=活体通过 相似度x.xx/阈值y.yy」。
系统那条通道改成「系统认证（指纹/人脸）」：`BIOMETRIC_WEAK | DEVICE_CREDENTIAL`，指纹、2D/3D 人脸、锁屏密码**任一通过**
即判为"系统认证通过"，并用设备密钥签发凭据（`payload.systemAuth=true`、`payload.authType` 区分生物识别/设备凭据）。
**应用无法指定模态**：`setAllowedAuthenticators` 只声明"允许哪些档位"，OEM 会挑最顺手的那个——录了指纹的机器一律先给指纹，
这是平台行为，不是权限或代码问题。要拿到"确实是这张脸"的证据，只有两条路：
① 设备人脸是 **BIOMETRIC_STRONG**（3D 结构光）时它本来就在强通道里；② 用前置相机那条（App 内活体 + 比对）。
现场想证明"手机自带人脸能走系统弹窗"的土办法：系统设置里临时删掉指纹、只留人脸，再点「系统认证」。
同一版还修了活体结果的口径：以前结果页把**全程** yaw 峰值当"转头"显示，没抽到转头也会出现 `转头 0.04`
（那是自然微动，转头阈值是 0.20），看起来像"没让转头却判了转头"。现在按**抽到的动作**分别给峰值
（`眨眼/转头/张嘴/微笑` 只在各自动作进行期间累计），没抽到的动作不显示；全程峰值单独标注"含自然微动，不作判据"。
同一版还补了两件事：① **识别日志一键导出**——每次卡背识别与 NFC 读卡都写本地日志
（`ocr-log-*.txt` / `nfc-log-*.txt`，含每行 OCR 原文与置信度、AID、MRZi、卡片 ATS/历史字节、APDU 条数、每步日志），
界面上「导出识别日志（OCR + 读卡，一键发微信）」会把两份合并成 `idcard-diag-*.txt` 并打成 **zip** 分享
（微信对 `text/plain` 的 content URI 支持不稳，zip 最可靠，也与「导出验证报告」同一形态）；
② **卡背 MRZ 三层兜底**——卡只占画面一小部分时把下半部放大 1.2~2.5 倍补扫；**MRZ 被检测模型切成碎片时**
（真机日志：`IDIRQAC6764` + 一堆碎块，最长 13 字符 < 26 字符门槛，于是全被丢掉），按"行组外接框"
整行重新识别一次（不是拼文本——右半段是乱码）；**只检出左半段时**（如 `IDIRQAC67` 只有 12 字符）
按行高估算整行长度把框向右扩再识别；连整行都检不出时才按水平条带跳过检测识别。
检测最长边也从 1280 提到 1600（真机帧是 2592×1944，压到 1280 后 MRZ 每字符只剩 7px）。
另外把 MRZ 片段从户号候选里剔除，避免报出假户号。
v3.12（versionCode 32）：**PACE 后半程按现场报文对齐**。
① **Nonce 解密不再强制 ISO9797 去填充**：§4.4.3.3 的 `7C 80` 通常是"密文比 s 多一块"，但这张卡只回
**16 字节**（没有填充）。现在规则是"密文只有一块 → 整段就是 s；多块 → 末尾是 `0x80 00…` 才剥离，
剥不掉也按原样用"，不再抛 `ISO9797 padding 缺失`。
② `s` 转大整数固定 `new BigInteger(1, s)`（无符号大端），最高位为 1 也不会变负数。
③ 四步 `GENERAL AUTHENTICATE` 的 CLA 按规范区分：**Step1~3 = `10 86 00 00`，Step4（T_PCD）= `00 86 00 00`**；
   某种 CLA 被回 6800/6E00 时自动换另一种重发。
④ PACE 建链后：SSC 全 0（AES 16 字节）→ 在 SM 下 `SELECT A0000002471001` → 读 EF.COM/DG1/DG2，不再回退 BAC。
NfcTest 新增 7l（16 字节 nonce + CLA 序列 10/10/10/00），NFC 用例 89 → **91**。
v3.11（versionCode 31）：**读卡顺序改为「PACE 优先，BAC 兜底」**。
① 贴卡后不再先发 BAC：`SELECT MF 3F00 → 读 EF.CardAccess(011C) → MSE:Set AT + GA（都在 MF 下）`，
PACE 建链成功后才 `SELECT A0000002471001` 读 DG；只有 PACE 返回**明确状态码**失败时才选应用回退 BAC
（BAC 的 `00 82` 有概率让这张卡掉电复位，一旦 TagLost 整次读卡就废了）。
② PACE 密码顺序改为 **MRZ 优先、CAN 次之**（OCR 的 MRZi 已过校验位，比人工输 CAN 可靠；AES-128 也比 3DES 省电）。
③ GENERAL AUTHENTICATE 先发 **`10 86 00 00 02 7C 00 00`**（命令链），回 6800/6E00 或无数据再退回 `00 86 …`。
④ `MODE_AUTO` 下不再对"无 EF.CardAccess"的卡盲试 14×2 组合——直接回退 BAC，省掉 1.8 秒无效等待。
⑤ IsoDep 超时 8000 → **2000ms**（避免单条无响应把线程挂 8 秒）；原始 APDU 日志上限 20 → **30** 条。
NfcTest：假芯片增加"不在 MF 就 6800"的约束；7h/7j/7k 改为按内容定位 SELECT AID（不再假设它是第 1 条）。

v3.6（versionCode 26）：**修掉 BAC 的 retail MAC 两处实现错误——这是"读卡必然中断"的真正根因**。
现场日志（`idcard-diag-20261110-190143`）里 `GET CHALLENGE` 正常返回 `90488D53E78041B0 9000`，
而 `EXTERNAL AUTHENTICATE` **整条没有响应**（TagLost @1066ms）。用 ICAO 9303-11 附录 D 的官方示例
（MRZ `L898902C<369080619406236`，E_IFD `72C29C…92F2`，M_IFD 应为 `5F1448EEA8AD90A7`）一验就露馅：
我们算出 `BB8F64A6EBE14CEB`。两处错误：① `Crypt.retailMac` 要求"已对齐"输入，而 BAC 算 `M_IFD` 时
**漏了 ISO 9797-1 padding method 2**（32 字节对齐数据必须再补一个 0x80 块）；② CBC-MAC 那一步
用的是 **3DES(K1,K2,K1)**，标准要求 **单 DES + K1**。客户端 MAC 错 → 芯片判定认证失败直接复位会话
（所以永远是 TagLost 而不是 6300），而同机另一个 App 的 MAC 正确，自然读得通。
同时把 `EXTERNAL AUTHENTICATE` 改回标准的 case 3（Lc=0x28、无 Le），芯片若要 Le 会回 `6C28` 自动重发。
NfcTest 新增官方向量断言（Kseed/Kenc/Kmac/E_IFD/M_IFD），NFC 用例 69 → **71**。
v3.5（versionCode 25）：**把原始 APDU 打进日志 + 用单测锁住 BAC 报文结构**。
`CardSession` 对**前 10 条** APDU 记录 `APDU #n → <命令 hex>` / `APDU #n ← <响应 hex>`（单条最多打印 64 字节，
超长标注总长），读卡失败时日志里能直接看到第 2、3 条到底发了什么、回没回 9000。NfcTest 新增 7h 断言：
① 第 1 条 `00A4040C07A0000002471001`（SELECT AID，P2=0C）；② 第 2 条 `0084000008`（GET CHALLENGE，Le=8，共 5 字节，
响应 8 字节随机数 + 9000）；③ 第 3 条 `00 82 00 00 28 <40 字节 E_IFD‖M_IFD>`（Lc=0x28、**无 Le**，
共 45 字节，ICAO 9303-11 §4.3 的 case 3；芯片若回 `6C28` 会自动按 Le 重发）；
④ 日志里确有 `APDU #2 ← …9000`。NFC 用例 64 → **69**。另外把 IsoDep 超时提为常量 `ISO_TIMEOUT_MS = 8000`
并在 NFC 日志头部记录「IsoDep 超时 / 存在性探测」两项配置，现场一眼能核对。
顺手修了编号口径：`SELECT AID` 以前绕过 `CardSession` 直接 `transceive`，既不计入 `apduCount` 也不进原始日志，
于是日志写「2 条 APDU」时其实已经发了 3 条。现在 SELECT 也走 session，编号与现场说的

v3.4（versionCode 24）：**读卡期间关闭平台的"存在性探测"**。现场日志 `idcard-diag-20261110-172839`（3.3-lite）：
`SELECT AID` 已成功，BAC 的 `GET CHALLENGE` 还没应答就 `TagLost`，全程 **1175ms ≈ 2 × 600ms** ——
正好是 `EXTRA_READER_PRESENCE_CHECK_DELAY=600` 的两个探测周期。也就是说"读卡中断"不是用户没贴稳
（现场贴了十几秒），而是**平台自己的探测往 ISO-DEP 会话里插低级命令，把这张 NFC-B 芯片复位了**。
现在把探测间隔设成 10 分钟（读卡期间等于关闭）：eMRTD 一次读卡 5~15 秒，不需要平台帮着看卡在不在；
卡真被拿走时下一条 APDU 照样抛 IOException。配套改动：读卡失败后自动**重开一次 ReaderMode**
（关掉探测后平台不会自己重新发现还贴着的卡；重开间隔 1.5 秒，给用户"拿开再贴"的时间，也避免高频自旋），
失败原因文字保留在屏幕上不被"感应中"覆盖。

（`BAC`/`PACE`/`READ`），不再让上层解析 `error` 字符串猜类型：TagLostException / IOException / APDU 超时
一律归"通信中断"，芯片明确回状态码（6300/6A81/6982…）才归"协议拒绝"。
② App 重试：**通信中断且断在 BAC → 重连后继续 BAC**（v3.1 那条"耗时 ≥2s 就跳过 BAC"的分支已删除，
它就是"超时后反而跳过 BAC"的根源）；只有上一轮 BAC 已被协议拒绝（断在 PACE 阶段）才跳过 BAC 直接探测 PACE。
③ 盲试提前退出：`EF.CardAccess` 不可用（6A82/6982）时若**首个** `General Authenticate` 返回 `6800`，
说明密码还没参与运算就被协议层拒绝 → 立即停止盲试（原 14×2 组合 = 33 条 APDU / 1.8 秒白等，
手持贴卡最容易在这段掉线），日志写明「判定不支持 PACE，停止盲试」。NfcTest 新增 7f（通信中断分类）
与 7g（6800 提前退出，断言 APDU ≤12），NFC 用例 59 → **64**。
v3.1（versionCode 21）：**取景加三道虚线参考区**（新增 `CardGuideView`）——① 整卡外框（蓝，按 ID-1 比例
85.6:54 横向居中，卡放进来就等于"占满画面"）；② 家庭编号区（黄，卡面数据行最后一行，值在左侧）；
③ MRZ 三行区（绿，卡底那三条机读行）。比例按真实卡背的版面反推：数据行 42%~52%、全息条 52%~58%、
MRZ 58%~81%。只做提示不参与识别；识别仍会自动定方向、自己找行。顺手修构建：`d8` 原先把几千个 `.class`
逐个列进命令行，这一次加到 `CardGuideView` 时正好超过 cmd.exe 的 8191 字符上限（"The input line is too long"），
现在先把 `build\classes` 打成 `build\classes.jar` 再交给 d8。
v3.0（versionCode 20）：**读卡流程重建为「卡背 MRZ 三行 → BAC 永远优先」**。现场日志
`idcard-diag-20261110-163945`：卡背 OCR 已全对（MRZi 与手输一致），但"有 CAN 就先走 PACE"
一读 `EF.CardAccess` 就 6982 → 下一条 APDU TagLost（354ms / 2 条 APDU），BAC 又被跳过；
同款卡用别的 App 只扫 MRZ 三行就能解锁，说明它是**普通 BAC 卡**。所以：`MODE_AUTO` 下 **BAC 一律先试**
（CAN 只决定 PACE 盲试的密码顺序），`EF.CardAccess` 只在 BAC 明确失败后才碰；TagLost 重连后按
"快断（<2s）重试 BAC / 慢超时（≈8s）才跳过 BAC"分流。OCR 侧补 TD1 第 3 行（姓名）展示，
界面同时显示 MRZ 三行与「姓名(MRZ)」，与对照 App 的识别区域（卡底三条机读行）一致。
NfcTest 7e 改为断言「有 CAN 也走 BAC、全程不碰 EF.CardAccess」。
v2.9（versionCode 19）：**梳理读卡流程、移除「拍证件正面（自动识别 CAN 码）」**。确定的标准流程是
**卡背 OCR（户号 + MRZ）→ MRZ 就绪自动开 NFC 感应 → 贴卡读芯片**，NFC 一步的前置只有卡背 MRZ 三项
（BAC/PACE-MRZ 密码由它们派生），户号只用于与 DG11 一致性比对，不是读卡的前置。正面 CAN OCR 删掉的理由：
正面有水印/全息标/斜拍反光，OCR 识别右下角 6 位数字并不稳，多一步反而拖慢流程；人工看一眼正面直接
「输入 CAN 码」手输更快也更准（手输后立即重试，有 CAN 时跳过 BAC 直接走 PACE-CAN）。
`CardFields.canCandidates` 与对应单测保留（协议能力不变，只是不再从相机帧上跑）。
同版补一个读卡回退（依据现场日志 `idcard-diag-20261110-143055`）：那张卡手输 MRZ + CAN 后，
`MSE:Set AT` 对 CAN/MRZ 都回 9000，但 `Get Nonce` 一律 6800——**Set AT 返回 9000 不代表芯片真支持 PACE**；
而旧逻辑"存了 CAN 就整场跳过 BAC"，导致 BAC 一次都没试。现在 MODE_AUTO 下 PACE 全失败时会**回退试一次 BAC**
（日志出现「PACE 全部失败，回退尝试 BAC」「BAC 回退成功」），NfcTest 新增 7e 用例覆盖这条回退链。
v2.6（versionCode 16）：真机首测修三处——①补 `USE_BIOMETRIC` 权限（不加就只有 `SecurityException`，不会弹指纹/人脸）；
②回执「改计数器」用例把值写死成 1（首次签发本来就是 1，等于没改）导致自测误判；③花名册「损坏回退 `.bak`」两个 bug：
首次导入不产生 `.bak`、校验和存在 SharedPreferences 里与旧版本 `.bak` 必然对不上 → 回退永远失败。另外把队列的
「单条本地开销」从"给一个 put 计时"（恒为 0µs）改成真实测量（序列化 + 状态迁移 + fsync 摊销）。

两个包是**两个不同的应用**（包名不同、桌面名称不同）：**可以同时装在一台手机上，后装的不再覆盖先装的**。
数据目录按包名隔离，所以各自的参照照片、阈值、调试图互不干扰——正好可以拿同一批照片在两个版本上各跑一遍做对比。
同一版本内的重复安装是原地升级（包名不变，桌面上的图标不会被复制成两个）。

顺带修掉一个旧隐患：以前两个包共用一份数据，从标准版换成精简版时 `SharedPreferences` 里的 `thr` 还在，`App.readModelConf()` 只在「没有 thr」时才写入默认值，于是精简版会沿用 0.45 而用不到它标定好的 0.58。包名分开后各存各的，阈值、参照特征、调试图都跟着版本走。

体积构成（标准版）：模型 166 MB + 原生库 30 MB（仅 arm64）+ MediaPipe 模型 3.6 MB + 代码 4.7 MB。
早先 225 MB 是因为同时打了 armv7 的库（+20 MB）；32 位机型已不再支持。

**精度差异（FairFace MiddleEastern 350 张，异人对）**：

| 模型 | 异人相似度均值 | 最大 | >0.45 占比 | FAR=1e-3 所需阈值 |
|---|---|---|---|---|
| R50 | 0.063 | 0.208 | 0.07% | ≈0.43 |
| MobileFaceNet | 0.216 | 0.390 | 3.24% | ≈0.58 |

小模型的嵌入空间更"挤"（异人均值高 3.4 倍），**所以不能沿用 0.45**——精简版默认 0.58 就是按 FAR≈1e-3 标定的。
另外注意：这是异人单侧分布，同人侧（FRR）需要真实人像对才能测，目前没有。

## 安装与测试

1. 把 `out/FaceVerify-offline.apk` 传到手机（微信/QQ 传文件、数据线、网盘都行），点击安装。
   - 需要允许「安装未知来源应用」。
   - 手机剩余空间要 ≥ 500 MB：APK 本身 224 MB + 首次启动会把 166 MB 模型复制到应用私有目录。
2. 首次启动会显示「复制模型…」，**约 5–20 秒**（视手机闪存速度），之后秒开。
3. **先点「自检」**（不需要相机/相册）：它会跑一遍检测→对齐→特征，显示每个环节的毫秒数与两个一致性数值，并把手里的 112×112 对齐结果画出来。这一步能直接确认模型在你机器上是否正常、跑得多快。把截图发我。
4. 点「① 从相册选择一张人像」→ 选一张你自己的清晰正脸照 → 等 1～3 秒，出现特征维度和建模耗时即成功。
5. 点「② 开始核验」→ 屏幕会显示相机画面（**所见即算法所见**）→ 按提示完成 3 个随机动作（眨眼／转头／张嘴／微笑中随机 3 个）。
6. 活体通过后自动采集 6 帧并比对，弹出结果：相似度、阈值、活体证据、耗时、调试图路径。
   采集时会做**几何门控**：5 点不合理（歪头/遮挡/误检）的帧不参与比对，并提示具体原因。
7. 可选「③ 评测模式」：多选一批人像 → 本地算出 FAR/FRR/EER 并给出建议阈值，一键应用到核验。
8. 可选「**双图比对**」：再选一张照片，与参照照片做 1:1 比对——**不需要相机**，用来单独验证核心算法。
   会输出相似度、阈值判定、各阶段耗时、检测点数、人脸占比、清晰度，以及两张对齐图并排。
9. 可选「**证件核验**」：卡背光学识别（家庭编号 + MRZ）+ NFC 读芯片。步骤见下面「证件核验」一节。
   只想验证芯片时，可以先在界面里手输 MRZ 三项（证件号/出生/有效期），不用相机。
10. 可选「**④ 技术验证实验室**」：一页把各 TV 条目的自测在本机跑一遍（设备环境、端侧可信性、回执防篡改、
   生物识别登录、动态码、离线花名册、离线核销队列），每项跑完显示判定与关键数字，最后「导出验证报告」
   生成 ZIP 并直接分享。装完机先跑这一页，把 ZIP 发回来就等于交了现场证据。
11. 实验室里三个「看得见」的入口：**强生物识别 / 人脸登录（前置相机）/ 系统认证（指纹/人脸）**、
   **看动态码 / 二维码**（60 秒一换，另一台手机可扫）、**查看花名册**（按户号搜索、点开看成员）。
   人脸登录会打开**前置摄像头**，按提示做 3 个随机动作；登记过参照人脸就给出 1:1 相似度，
   没登记则明确标注"仅活体、未绑定身份"。系统认证走系统弹窗（指纹/人脸/密码任一，模态由系统决定）。

**验证"不联网"**：开飞行模式，整个流程照样跑通（模型、推理、比对全在手机本地）。

### 出问题时怎么反馈

- 主界面底部会自动显示上一次崩溃的堆栈（`last_crash.txt`），截图发我就行。
- 每次核验完会存一张**调试图**（参照照片 + 本次各帧的 112×112 对齐结果并排），路径写在结果页里：
  `Android/data/<包名>/files/debug/verify_*.png`（标准版 `<包名>` = `iq.digitalration.faceverify`，精简版 = `iq.digitalration.faceverify.lite`）。这张图能直接看出对齐有没有歪。

## 证件核验（卡背 OCR + NFC 芯片）

主界面「证件核验（卡背 OCR 家庭编号 + NFC 芯片）」进入，一个界面做两件事，对应两张参考截图。

### ① 卡背光学识别（v2.3，后置摄像头，离线不联网）

**要认的第一个东西是「家庭编号」**，也就是卡背 `الرقم العائلي :` / `ژمارەی خێزانی :` 后面那个
18 位编号。两位真实样例说明它**不是纯数字**：

```
1002 E 6996574360150     4 位数字 + 1 位字母 + 13 位数字
1002 L 00M9770006805     4 位数字 + 1 位字母 + 13 位"字母数字"（尾部还可以带字母）
```

所以规则是：**前 4 位必须是数字，第 5 位必须是字母，后 13 位是字母数字**（数字 ≥13、字母 ≤4）。
尾部字母只有在"不像数字"时才保留（M/C/F/H/K/N/R/U/V/W/X/Y），像数字的字母（O/I/S/B/Z/G/D/Q/T/A/E/P）
才按置信度决定是否改成数字。

v2.2 相比 v2.0/v2.1 的改动（v2.0 用中文 PP-OCRv4 模型，对卡面数字和阿拉伯文都不太行）：

| 改动 | 为什么 |
|---|---|
| 识别模型换成 **en_PP-OCRv3_rec**（436 类 ASCII）+ **arabic rec**（161 类阿拉伯字母）双模型 | 中文模型的 6625 类里全是汉字，18 位数字长串会被汉字类抢票；英文模型字符集只有 ASCII，数字行一次过的比例高得多。阿拉伯文模型专门读标签 |
| CTC 解码加**白名单**（只用 0-9 A-Z `<`） | 去掉小写字母、标点、汉字的干扰，`l` 不再抢 `I` 的位置 |
| 低置信度行自动**二值化重试**（Otsu） | 卡面底纹/水印/反光把笔画和背景拉近时，二值化后识别率明显上升 |
| 缩放换成**面积平均 + 双线性**（原来是最近邻） | 最近邻会让小字号出现马赛克、大字号出现摩尔纹，两个都伤识别 |
| **认标签再认值** | 只在「الرقم العائلي / ژمارەی خێزانی」那一行（或紧邻的左/下一行）里找编号，避免把卡上别的长数字当成户号。标签归一化后模糊匹配（`ژ→ز`、`ێ→ي`、`ە→ه`，编辑距离 ≤2） |
| 家庭编号**位置感知纠错 + 代价** | 前 4 位按数字修、第 5 位按字母修，改动 ≤3 处才接受；依旧不靠"猜" |
| MRZ 用**校验位反解** | 在 `0↔O、1↔I、5↔S、8↔B、2↔Z、6↔G、4↔A、7↔T、3↔E、9↔P` 里枚举 ≤2 处替换，找到让 ICAO 7-3-1 校验位成立的组合——一个字符读错不再毁掉整张卡的 BAC 密码 |
| 连拍 **2 帧投票** | 点一次「拍摄识别」取最近 2 帧；第一帧就"户号 + MRZ 齐全"时不再跑第二帧。同一位错成同一个字符的概率低，逐位取多数能修掉单帧错误 |
| **多尺度集成**（v2.3） | 长 alnum 行（户号/MRZ/日期）在 1.0×、1.35× 宽度和原图/二值化上各识别一次，逐位按该位的模型概率加权投票。`M→4` 这类错误在不同尺度上不会同时发生，集成后多数能被纠正 |
| **歧义位给候选 + 手工改正**（v2.3） | 逐位记录次优字符，把"4 也可能是 M"这类位置列成候选值显示在界面上；另加「改正家庭编号」输入框，人工一眼能改对。读芯片后若 DG11 与光学值只差 1~3 位，直接判为 OCR 认错、以芯片为准并说明差异位置 |

其它行为不变：

- 取景有三道**虚线参考区**（v3.1 起，v3.3 按真实卡背照片重新定位）：蓝色整卡外框（ID-1 比例）、
  黄色家庭编号区（卡高 44%~53%）、绿色 MRZ 三行区（卡高 71%~93%）；框上不带文字，提示只在顶部一行。
  框只做对齐提示，算法不依赖它在不在。
- 拍照用**后置摄像头**；界面是"当前帧定格预览"，卡对好框后**稳 0.3 秒再按**。没有后置自动退回前置并提示。
- 照片**横着拍/倒着拍都能认**：先用 480px 小图在 0/90/180/270 比较"文字概率面积"选方向，
  单行再用二阶矩定轴 + 逐行 0°/180° 试别（阿拉伯文行会标记 `rtl`，输出前整体反转成正常阅读顺序）。
- 认不出 MRZ 时「手输 MRZ」兜底（证件号 / 出生 YYMMDD / 有效期 YYMMDD），读芯片不依赖相机。

| 环节 | 选型 | 体积 |
|---|---|---|
| 文字检测 | PP-OCRv4 det（DBNet，ONNX，1280 最长边） | 4.5 MB |
| 编号/MRZ 识别 | en_PP-OCRv3_rec（CTC，436 类 ASCII，行高 48） | 7.5 MB |
| 阿拉伯文标签识别 | arabic rec（CTC，161 类） | 8.6 MB |
| 字典 | `ppocr_keys_en.txt` / `ppocr_keys_ar.txt` | 2 KB |

模型来自 HuggingFace `monkt/paddleocr-onnx`（PaddleOCR 官方模型的 ONNX 导出版；检测模型沿用
`SWHL/RapidOCR` 的 PP-OCRv4 det）。全部塞在 `assets/`，运行时零网络、零 GMS——**飞行模式下可用**。
推理走 App 已有的 ONNX Runtime（与 ArcFace 同一个 native 库），没有引入新的原生依赖。

### ② NFC 读 ICAO 9303 芯片（靠近自动读）

**是"贴上去自动读"，不用反复点按钮**：MRZ 一就绪（OCR 成功或手输完成），App 会自动打开 NFC 感应
（`NfcAdapter.enableReaderMode`），此后把卡贴到手机 NFC 区域就自动开始读；读成功后自动关闭感应
（避免重复触发），失败则保持感应，重新贴一次即可重试。切到后台或退出页面会关闭感应，回来时自动恢复。

- 贴卡位置：多数机型在**背面上半部、摄像头附近**；不确定就左右上下慢慢挪，感应到会有系统提示音。
- 必须保持贴合：读 DG2 人像要发上百条 APDU，**5~15 秒**，中途拿走会中断（提示"读卡中断，可重贴重试"）。
- NFC 没开时界面会直接告诉你去系统设置打开，回来后自动恢复感应。
- 感应到的是普通 NDEF 标签（不是证件芯片）时会明确提示"不是 ISO-DEP 芯片"，不会误报成功。

芯片读出的内容：

- **DG1**：机读区（证件号、签发国、国籍、出生、性别、有效期、姓名 + 各校验位）
- **DG2**：芯片内人像（JPEG 可直接显示；JPEG2000 在 Android 上无系统解码器，只显示字节数并说明原因）
- **DG11**：附加信息（全名、个人编号/家庭编号——**和光学识别的家庭编号做一致性比对**、完整出生日期、出生地、地址等）
- **EF.SOD**：CMS 签名 + 各数据组哈希，给出四项判定（对应参考截图里的"芯片状态"）：

| 判定项 | 本 App 的做法 | 含义 |
|---|---|---|
| SOD 完整性认证 | 用 SOD 内自带的证件签名证书验 CMS 签名（含 signedAttrs 的 messageDigest） | SOD 未被篡改 |
| 数据组哈希（芯片认证） | 对读到的 DG1/DG2/DG11 重算哈希，与 SOD 声明值逐个比对 | 芯片数据未被改写 |
| 证书链自洽 | DS 证书的签发者能在 SOD 内找到且签名可验证 | 链自洽，**但未锚定 CSCA** |
| 签名证书有效性 | `X509Certificate.checkValidity()` | 当前时间在证书有效期内 |

> 「这张证件由伊拉克签发」必须导入伊拉克的 CSCA 主列表才能判定，本版**没有**主列表，
> 所以只报"自洽/未锚定"，不会把"签名有效"说成"证件真实"。

**主动认证（AA）与 CSCA 锚定（v3.4 新增）**

| 能力 | 做什么 | 界面怎么看 |
|---|---|---|
| 主动认证 AA | EF.COM 声明 DG15 时读公钥，发 8 字节**随机**挑战（`00 88 00 00 08 …`），用芯片公钥验签（RSA SHA-1/256/384/512、ECDSA 依次试） | 「主动认证（AA · 防克隆）」：✓ = 芯片真的持私钥，**整套 DG 数据被复制到别的芯片过不了这一步**；未声明 DG15 = 该证件不支持 |
| CSCA 锚定 | 把 SOD 里 DS 的签发者证书与本地受信 CSCA 库比对（**公钥指纹优先**，其次 Subject+序列号） | 「CSCA 锚定：✓ 已锚定 C=IQ」才是"由该国签发"；「未收录」= 只证明自洽 |

CSCA 库放置方式：`app/assets/csca/*.pem`（ICAO PKD MasterList 导出、或本国边检下发的证书包，
多张可以串在一个文件里），启动时自动装入并在 logcat 打印张数。库为空时行为与之前完全一致，
只是把"未锚定"写得更明确。

访问控制顺序（v3.0 起固定）：

1. **BAC 永远先试**（3DES 安全报文，密码 = MRZ 三要素）——它兼容面最广，现场那张卡就是普通 BAC 卡。
   **不管有没有存过 CAN，第一步都是 BAC**；`EF.CardAccess` 在整个 BAC 阶段一条 APDU 都不发。
2. BAC 明确被拒（状态字，如 `6300`）后才探测 **PACE-ECDH-GM**（AES-128/192/256、3DES）：
   先读 EF.CardAccess 拿芯片声明参数，拿不到就按常见 OID/曲线盲试；有手输 CAN 时盲试顺序是
   **CAN → MRZ**（ICAO：0x02=CAN、0x01=MRZ）。
   支持 NIST P-192~P-521 与 brainpool P192r1~P512r1（曲线参数内置，**不依赖 JCE 的 brainpool 支持**，
   Android/Conscrypt 与 JDK/SunEC 对 brainpool 的支持并不一致）。
3. 未实现：PACE-DH-GM、PACE 的 Integrated/Chip Authentication Mapping。遇到只支持这些的芯片，
   界面会明确报"PACE 失败"，不会静默失败。

**为什么 CardAccess 必须排在 BAC 后面**：现场两次日志都显示，这张卡收到 `SELECT EF 011C` 回 `6982`
之后，下一条 APDU 立刻 `TagLost`（354ms / 2 条 APDU），会话被芯片复位——先探测 PACE 就等于把
唯一能走通的 BAC 路堵死。

### 交给同事测试的 6 步（请连同样机说明一起发）

1. 装 `FaceVerify-lite.apk`（包名 `iq.digitalration.faceverify.lite`，可与旧版共存）。
2. 手机**打开 NFC**（设置 → 连接 → NFC），系统版本 Android 7.0 以上。
3. 进「证件核验」→ 允许相机 → 把卡背放进框里，点「拍摄识别」。
4. 看顶部状态：出现"MRZ 已就绪 / NFC 自动感应中"就说明可以读芯片了；
   若提示"MRZ 不完整"，点「手输 MRZ」把证件号/出生/有效期填进去（卡背 MRZ 里都有）。
   **如果读卡一直失败（BAC 挂起约 8 秒 / EF.CardAccess 被 6982 挡住）**：点
   「输入 CAN 码（证件正面）」——ICAO 允许芯片把 PACE 密码设成卡片正面的 **CAN**（通常 6 位数字），
   这时只用 MRZ 是进不去的。人工看一眼证件正面右下角，把那串数字输进去后会自动重试。
5. **贴卡**：卡背（有照片那面）贴到手机背面上半部，保持 10 秒左右，听到提示音后不要马上拿走。
6. 把屏上这几段截图发回：①家庭编号与 MRZ 那几行 ②"NFC 感应/读取"状态文字
   ③DG1/DG2/DG11 与"被动认证"那几行（失败时也要整段截图，错误信息就是我要的）。
   **若读卡失败且日志显示 BAC 报错（不是 TagLost），随后 EF.CardAccess 也被拒**：这张卡可能把 PACE 密码
   设成了 **CAN**——看一眼证件**正面右下角的那串数字**，点「输入 CAN 码」手输，再贴卡（BAC 仍会先试一次，
   失败后 PACE 盲试会用 CAN）。
7. 识别/读卡不顺时，点 **「导出识别日志（OCR + 读卡，一键发微信）」**，把生成的
   `idcard-diag-*.zip` 发回——里面有每行 OCR 原文（含置信度）、卡片 ATS/历史字节、APDU 条数与每一步日志，比截图完整。

### 读卡失败怎么排查（v2.8 现场实测）

现场出现过这一串，先分清哪一句是"正常回退"、哪一句才是真失败：

```
应用 A0000002471001 已选中                                  ← 通
EF.CardAccess 读取失败(选择 EF011C 失败:6982 安全状态不满足)  ← 正常：芯片不开放 EF.CardAccess，按无 PACE 走 BAC
BAC 认证 失败:TagLostException: Tag was lost.               ← 真失败：卡离开/移动了感应区
```

- `6982` 不是错误：ICAO 里"不支持 PACE"通常回 `6A82`，这批卡回 `6982`，两种都按"无 PACE"处理。
- `TagLost` 只能是物理断连（MRZ 输错会回 `6300`；卡只支持 PACE 会回 `6982/6A81`）。
- 现场按这个顺序试：**贴牢 10 秒别动** → **去掉手机壳**（尤其磁吸/金属） → **换位置慢慢挪**（背面上半部、摄像头附近） →
  确认 **MRZ 三项与卡面一致** → 仍失败就把界面上的 **ATS/历史字节 + APDU 条数** 截图。
- v2.8 已把 presence check 从 250ms 调到 600ms、6982 不再显示为"读取失败"；并且**改成 BAC 优先**——
  真机日志显示"先读 EF.CardAccess"会让芯片在回 6982 之后直接断连（349ms / 2 条 APDU 就 TagLost），
  所以现在先试 BAC，只有 BAC 被拒才去探测 PACE。
- 读卡过程中顶部每秒刷新「读卡中… 已 N 秒」，结束显示「读卡失败 · 349ms · 2 条 APDU」——
  一眼就能分清"没贴够"和"芯片复位"。
- 重试策略看**失败类型**，不看耗时（v3.2）：`TagLost` / `IOException` / APDU 超时 = 芯片没给状态码，
  重连后**继续 BAC**；只有芯片明确回状态码（`6300` / `6A81` / `6982`）= BAC 已被拒，才跳过 BAC 探测 PACE。
  日志里的「失败分类」一行会直接写 `FAIL_TRANSPORT` 还是 `FAIL_PROTOCOL`。
- 盲试会**提前收手**：`EF.CardAccess` 不可用、且首个 `General Authenticate` 就回 `6800`，说明密码还没参与
  运算就被协议层拒绝（换曲线/换密码不可能过），日志写「判定不支持 PACE，停止盲试」，不再空跑 14×2 组合
  （原来要 33 条 APDU / 约 1.8 秒，手持贴卡最容易在这段掉线）。
- **PACE 密码支持 CAN**：ICAO 里密码参考 0x01=MRZ、0x02=CAN。v2.9 起不再"有 CAN 就跳过 BAC"——
  现场 v3.0 日志（16:39）证明这张卡是 BAC 卡，跳过 BAC 只会踩 `6982 → TagLost`。
- v2.9 移除了「拍证件正面（自动识别 CAN 码）」：正面水印/全息标/斜拍让这块 OCR 不稳，
  人工看一眼再「输入 CAN 码」手输更快更准；手输值写入 `cfg.can`，只影响 PACE 盲试的密码顺序。

### 这一块没验证的地方（重要）

1. **没有真机 NFC**。APDU 层只在"假芯片"上跑通；真实卡的时序、`6Cxx`/`61xx` 兼容性、
   读 30KB 人像要多久（约 150 条 APDU）都只能在手机上确认。
2. **没有真实卡背照片**。OCR 只在合成图上验证（Arial 近似的印刷体），真实卡面的底纹、阿拉伯文、
   反光、竖排字号都可能让检测框变差；家庭编号的格式也只有截图这一种样例。
3. **JPEG2000 人像解不出来**。Android 的 BitmapFactory 不支持 JP2，如果芯片用 JP2，只能看到字节数。
4. **没内置任何国家的 CSCA 证书**（机制已有，见上文「CSCA 锚定」）。库为空时"被动认证"只能证明
   "数据与 SOD 一致、SOD 签名自洽"，不能证明证件由某国签发；把对应国家的 PEM 放进 `assets/csca/` 后才能判定。
5. **AA 只在合成数据上验过签名算法**（RSA/ECDSA 的验签 + 篡改/换挑战拒绝），没有真实卡的 DG15 联调；
   芯片对 `INTERNAL AUTHENTICATE` 的返回码（6982 未启用 / 6A81 不支持）按规范做了区分，真机需确认。

## 技术方案

| 环节 | 选型 | 为什么 |
|---|---|---|
| 人脸检测 + 网格 | **MediaPipe Face Landmarker**（`face_landmarker.task`, float16, 3.5 MB）478 点 + 52 blendshape | Face Mesh 本身只给几何，但它的 blendshape 直接输出 `eyeBlinkLeft/Right`、`jawOpen`、`mouthSmile`，比手算 EAR 稳；活体判定就是靠它 |
| 活体 | **挑战-响应**：从 {眨眼, 转头, 张嘴, 微笑} 里随机抽 3 个，顺序随机，每个都有超时重试 | 静态照片无法在时序上完成眨眼/转头；随机顺序防预录视频 |
| 人脸对齐 | 5 点相似变换（Umeyama）→ 112×112，模板与 insightface `norm_crop` 完全一致 | ArcFace 对对齐极敏感，用官方模板才能吃到模型原精度 |
| 特征提取 | **ArcFace R50 @ Glint360K**（`w600k_r50.onnx`, 166 MB, ONNX Runtime 1.20 CPU）512 维 | 比 MobileFaceNet 精度高一大截，且只在前几帧跑一次，延迟可接受（实测见下） |
| 比对 | 余弦相似度，多帧平均 + 水平翻转 TTA | 平均 6 帧降噪，翻转 TTA 消掉对齐镜像误差 |

管线：`相机帧 → MediaPipe(478点+blendshape+yaw) → 5点对齐 112×112 → ArcFace → L2 归一化 → 与参照照片特征算余弦 → 阈值判定`

所有资源都在 APK 里（`assets/`），零网络依赖，零权限除了相机（选图走系统 `ACTION_OPEN_DOCUMENT`，不需要存储权限）。

## 已经验证过的部分（桌面复现，非手机）

因为这台机器没有可用的 adb 设备，**以下都是在 PC 上用 onnxruntime 跑同一个 `.onnx` 得到的**，代码路径与 App 内一致：

- **模型接口**：`w600k_r50.onnx` 输入 `[N,3,112,112]`、输出 `[1,512]`；预处理 RGB + `(x-127.5)/127.5` + NCHW，与 insightface 官方一致。
- **特征判别力**（LFW 8 个不同身份，28 对）：
  - 不同人：均值 **0.063**，最大 0.208
  - 同一张图水平翻转（等同"同一人"）：均值 **0.827**
  - → 0.45 的默认阈值落在这两个分布中间，留有余量。
- **对齐算法**：把图旋转 20° 后用"同样旋转后的 5 点"重新对齐，两张 112×112 裁剪余弦 **0.997** → Umeyama + 双线性 warp 无错。
- **对齐对关键点误差的敏感度**（250px 人脸，单点沿 x/y 各偏 d 后与原裁剪比，n=6）：

  | 偏移 | 3px | 6px | 12px | 20px |
  |---|---|---|---|---|
  | 眼外角 | 0.987 | 0.969 | 0.931 | 0.878 |
  | 鼻尖 | 0.994 | 0.985 | 0.964 | 0.930 |
  | 嘴角 | 0.991 | 0.979 | 0.953 | 0.912 |

  → MediaPipe 的正常定位误差（1~3px）只影响 <1.5%，**关键点索引选偏几个像素不会毁掉精度**；鼻尖最不敏感，眼睛最关键。
- **APK 结构**：`resources.arsc` 未压缩且 4 字节对齐、native 库未压缩、v2+v3 签名校验通过、关键类（MediaPipe/ORT/guava）都在 dex 里。
- **FAR/FRR 统计代码**（`Stats.java` 不依赖 Android，直接 `main()` 自测）：
  - 完全可分数据 → EER **0.00%**，目标 FAR 阈值落在两类之间；
  - 高斯分离（μ=0.62 vs 0.12，σ=0.10）→ EER **0.25%**（与理论 Φ(-2.5)=0.62% 同量级，样本 400 的分辨率就是 0.25%）；
  - 高度重叠（μ=0.40 vs 0.30，σ=0.12）→ EER **34.9%**（理论 ≈34%）→ 公式实现正确。

## 没验证、也别当真的部分（很重要）

1. **没有真机跑过**。相机旋转、帧率、机型差异这些只能上手机才知道。所以我把预览改成"直接显示算法分析帧"，方向错了肉眼立刻能看出来，也能在设置里手动改旋转。
2. **被动反欺诈（打印/屏幕翻拍）没做**。我下载并实测了一个公开的 MiniFASNetV2 ONNX，**在 4 种预处理下输出恒定（0.99 全给同一类），对真脸和屏幕翻拍零区分度**——是个坏模型，所以我把它删了，没有拿假分数糊弄。现在能防的是"静态照片 + 简单视频"，**防不住高质量视频重放**，那必须上经过样本训练的被动模型（见下文）。
3. **伊拉克人群精度没测过**。这版用的是 Glint360K 训练的通用模型，中东人脸在训练集里有覆盖但不是重点；理论性能会略低于官方 LFW 99.8%。**要"保证准确率"必须用真人数据标阈值**，见下节。
4. **证件核验（OCR + NFC）没有真机和真卡验证**。OCR 只在合成卡背图上跑通；NFC 协议栈只在"假芯片"上跑通（详见「证件核验」一节的未验证清单）。

## 怎么把精度"适配伊拉克人"

阈值 0.45 是通用起步值，别直接当 KPI。正确做法（App 已具备条件）：

1. 收集本地数据：**每人 2–3 张**（不同时间/光照/角度）+ 若干"非同人"对照，至少 30–50 人、上千对。
2. 把照片放进手机，文件名按 `人名_序号.jpg` 命名（`iraq001_a.jpg`、`iraq001_b.jpg` 为同一人）。
3. App 里点「③ 评测模式 → 选择照片（可多选）」→ 自动输出同人/异人分布、ROC 表、EER、以及按目标 FAR 的建议阈值 → 点「应用建议阈值」直接生效。
4. 选 FAR 档位：
   - 门禁/核身类（误接受要极低，FAR=1e-3）→ 阈值通常 0.50~0.55
   - 体验优先（FAR=1e-2）→ 0.40~0.45
5. 记录 EER 作为基线。若 EER 明显差于 3%~5%，再考虑换模型（见下）。

下一步可选的模型升级（都需要联网下载，本次未做）：
- `buffalo_l` 的 `w600k_r50`（也就是现在这个）已是最常用的高质量开源档；
- 想再进一步：`glintr100`（R100，248 MB）或 adaface/Arc2Face 系列；
- 想更快：`w600k_mbf`（13 MB，精度降 1~2%），适合低端机。

## 重新构建

```powershell
pwsh -File tools\build.ps1               # 标准版 R50  → out/FaceVerify-offline.apk  包名 iq.digitalration.faceverify
pwsh -File tools\build.ps1 -Model mbf    # 精简版 MBF  → out/FaceVerify-lite.apk     包名 iq.digitalration.faceverify.lite
pwsh -File tools\test.ps1                # JVM 单测（对齐矩阵/活体状态机/FAR 统计）
```

**模型 → 应用标识**的映射写在 `tools/build.ps1` 的「每个模型 = 一个独立应用」段：默认 r50 用原包名（保留升级路径），mbf 加 `.lite` 后缀，桌面名称分别是「离线人脸核验 R50 / Lite」。
包名是通过 `aapt2 link --rename-manifest-package` 在生成 APK 时改的，`app/AndroidManifest.xml` 和 Java 源码都不用动（R 类仍在 `iq.digitalration.faceverify` 下）。
要临时换个标记（比如同时留多个试验包）可加参数：`-PackageSuffix .r50test -AppLabel "核验 R50 试验" -Out FaceVerify-r50test.apk`。
新增模型时：在 `param` 的 `ValidateSet` 里加名字，并在同段给出对应的包名后缀/桌面名/默认阈值。

依赖已经在本机准备好（`sdk/` 里是 JDK17 + build-tools 35 + platform 35，`dl/maven` 里是 MediaPipe/ORT 的 AAR）。注意：`aapt2` 遇到绝对中文路径会报 `Illegal byte sequence`，脚本已全部改用相对路径，别改回去。

构建还需要 `models/` 下的 OCR 资源：`ppocr_det.onnx`、`ppocr_rec.onnx`、`ppocr_keys_v1.txt`（脚本会检查，缺了直接报错）。
`EcCurve.java` 是生成文件：改曲线请改 `tools/gen_curves.py` 后重跑（NIST 参数取自 JDK，brainpool 取自 RFC 5639）。

`tools/build.ps1` 存成 **UTF-8 with BOM**：本机是 PowerShell 5.1，它会把**没有 BOM** 的 `.ps1` 按系统 ANSI 解码，脚本里的中文（默认阈值说明、桌面名称）就会变乱码并写进 APK。用编辑器改完请确认 BOM 还在。

## 后续建议

- 拿到你的真机反馈后，优先修：相机旋转、帧率、首启复制耗时。
- 要做"能防翻拍"的版本，需要一批真实的攻击样本（打印照片、手机屏幕、iPad 回放），再训练/微调一个被动模型——这是目前最大的缺口。
- 想上线级应用，还要补：活体动作的防注入（摄像头帧签名）、特征加密存储、活体与比对的时序绑定。
